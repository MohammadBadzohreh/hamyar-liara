# کشف API و طرح اولیه دستیار لیارا

تاریخ بررسی: ۲۰۲۶-۱۰-۲۲. وضعیت: بررسی مستندات عمومی؛ هیچ API احرازهویت‌شده روی حساب آزمایش نشده است. کاربر ورود به کنسول را کامل کرده و مشاهده خواندنی پنل انجام شد. در بخش پلتفرم تیم فعال هیچ برنامه‌ای وجود ندارد. موجودی در پنل دیده شد؛ مقدار آن برای جلوگیری از انتشار اطلاعات حساب در سند عمومی ثبت نمی‌شود. ویدئوی اصلی مسابقه در اختیار نیست؛ نیازمندی‌ها از متن ارسال‌شده استخراج شده‌اند.

## منابع و فایل‌ها

- مخزن رسمی: https://github.com/liara-cloud/openapi
- مستندات: https://openapi.liara.ir/ و https://developers.liara.ir/
- مشخصات دریافت‌شده: `api/paas.yaml`، `api/dbaas.yaml` و `api/dns.yaml` از شاخه main مخزن رسمی در تاریخ بالا. این‌ها snapshot هستند، نه تضمین رفتار سرویس زنده.
- فایل `api/ENDPOINTS.md` فهرست مسیرها و متدهای استخراج‌شده را نگه می‌دارد.

## APIهای اصلی MVP

آدرس پایه PaaS در مشخصات: `https://api.liara.ir`. احراز هویت Bearer token در هدر Authorization؛ کلید فقط در بک‌اند نگه‌داری شود.

| نیاز | متد و مسیر | سیاست پیشنهادی |
|---|---|---|
| فهرست برنامه‌ها | GET /v1/projects | خواندن خودکار |
| جزئیات برنامه | GET /v1/projects/{name} | خواندن؛ حذف اسرار از خروجی |
| ساخت برنامه | POST /v1/projects | تأیید پلن، هزینه و مقصد |
| ارسال سورس | POST /v2/projects/{name}/sources | در محدوده انتشار تأییدشده |
| انتشار | POST /v2/projects/{name}/releases | تأیید نسخه و مقصد |
| لاگ | GET /v1/projects/{name}/logs | خواندن؛ since اجباری؛ حذف اسرار |
| رویدادها | GET /v1/projects/{name}/events | خواندن خودکار |
| نسخه‌ها | GET /v1/projects/{name}/releases | page و count اجباری |
| نمونه‌های برنامه | GET /v1/projects/{name}/applets | خواندن خودکار |
| خلاصه منابع | GET /v1/projects/{name}/metrics/summary | خواندن خودکار |
| CPU | GET /v1/projects/{name}/metrics/cpu | since عددی اجباری |
| RAM | GET /v1/projects/{name}/metrics/memory | since عددی اجباری |
| متغیر محیطی | POST /v1/projects/update-envs | تأیید تغییر؛ مقادیر محرمانه مخفی |
| تغییر پلن | POST /v1/projects/{name}/resize | تأیید هزینه؛ planID لازم |
| ری‌استارت | POST /v1/projects/{name}/actions/restart | تأیید وقفه احتمالی |
| روشن/خاموش | POST /v1/projects/{name}/actions/scale | تأیید |
| دامنه‌ها | GET و POST /v1/domains | خواندن خودکار؛ تغییر با تأیید |
| گواهی SSL | POST /v1/domains/provision-ssl-certs | در محدوده اتصال دامنه تأییدشده |

انتشار دو مرحله دارد: بارگذاری فایل gz در sources و دریافت sourceID؛ سپس ایجاد release با sourceID، port و type طبق schema. پذیرفته‌شدن درخواست با سالم‌بودن سایت یکسان نیست؛ وضعیت نسخه، رویدادها و HTTP مقصد باید بررسی شوند.

## نتیجه بررسی تکمیلی

گزارش جدید `ACCOUNT-READINESS.fa.md` مرجع وضعیت فعلی است: API پلن‌ها `/v1/me`، اعتبار `/v1/billing`، لاگ v2 و لاگ build در منابع رسمی پیدا شدند. انتخاب bundlePlanID و محدودیت ۷روزه دامنه موقت نیز ثبت شده‌اند. موارد زیر وضعیت بررسی اولیه را منعکس می‌کنند و در گزارش جدید تکمیل شده‌اند.

## ابهام‌های بررسی اولیه

- فهرست قیمت و مشخصات پلن‌ها، موجودی حساب و محدودیت اعتبار مسابقه: در بررسی فعلی endpoint تأیید نشده؛ نبودن در این فهرست اثبات نبودن API نیست. ابتدا پنل/مستندات رسمی و در صورت نیاز پشتیبانی.
- واحد CPU و RAM، معنای since، بازه نگهداری لاگ و شکل پاسخ واقعی: با نمونه سرویس آزمایشی بررسی شود؛ مقدار خالی به معنی مصرف صفر نیست.
- لاگ runtime با لاگ build یکی نیست؛ دسترسی به لاگ ساخت باید جداگانه تأیید شود.
- rollback مستقیم، webhook رخدادها، اتصال GitHub و دامنه دسترسی توکن: هنوز تأیید نشده‌اند.
- API لیارا برای DNS، جایگزین دسترسی به پنل ثبت‌کننده دامنه نیست. تغییر nameserver در ایرنیک ممکن است مرحله دستی باشد.
- محدودیت نرخ درخواست و timeout نیازمند بررسی عملی‌اند؛ retry محدود و backoff لازم است. عملیات نوشتن پس از timeout کورکورانه تکرار نشود.

## دامنه پیشنهادی MVP

یک دستیار فارسی با دو مسیر کامل برای یک پروژه نمونه Node.js:

1. بررسی پروژه ← شناسایی نیازها ← پیشنهاد پلن با دلیل و هزینه معتبر ← تأیید کاربر ← ساخت/تنظیم/انتشار ← بررسی HTTP ← ارائه آدرس.
2. درخواست «سایتم خطای ۵۰۰ می‌دهد» ← جمع‌آوری لاگ، رویداد، آخرین انتشار و منابع ← فرضیه‌های رتبه‌بندی‌شده با شواهد ← پیشنهاد اصلاح ← تأیید ← اجرا ← بررسی دوباره.

نمونه خطای دمو می‌تواند متغیر محیطی ضروریِ غایب در یک مسیر برنامه آزمایشی باشد. تشخیص باید از لاگ واقعی بیاید؛ رفع آن نیز با API واقعی انجام شود. نمونه از پیش آماده و خطای عمدی در ارائه شفاف اعلام شود.

پایش دائمی LLM لازم نیست. در MVP کاربر تحلیل را فعال می‌کند؛ بعداً health checker سبک می‌تواند هنگام رخداد، تحلیل را فعال کند. ادعای اطلاع خودکار از خرابی بدون trigger واقعی مطرح نشود.

## معماری پیشنهادی

رابط گفت‌وگو و کارت تأیید ← بک‌اند TypeScript ← هماهنگ‌کننده گردش‌کار و مدل ← ابزارهای محدود لیارا.

مدل پیشنهاد و تحلیل می‌دهد. لایه اجرای بک‌اند مستقلاً مجوز، مقصد، پارامترها و انقضای تأیید را کنترل می‌کند. تأیید باید به همان عملیات و پارامترها متصل باشد؛ تغییر پیشنهاد تأیید را باطل می‌کند. ثبت رویداد عملیات، جلوگیری از اجرای دوباره و بررسی نتیجه ضروری است.

لاگ‌ها ورودی غیرقابل‌اعتمادند؛ دستور داخل لاگ نباید اجرا شود. اسرار پیش از ارسال به مدل حذف شوند. توکن لیارا وارد مرورگر، prompt یا Git نشود. مسیر اجرای shell آزاد برای MVP لازم نیست.

اتصال به coding agent فاز بعد: بسته شواهد و بازتولید خطا ← patch در شاخه جدا ← تست ← نمایش diff ← تأیید انتشار. اصلاح کد به معنای رفع قطعی حادثه نیست؛ نتیجه روی سرویس بررسی شود.

MCP می‌تواند بعداً همان ابزارهای بک‌اند را عرضه کند؛ برای MVP ساخت هم‌زمان چند رابط ضروری نیست.

## اطلاعات موردنیاز از حساب

- مقدار و تاریخ انقضای اعتبار مسابقه و خدمات مجاز؛ بدون ذخیره مشخصات پرداخت.
- حساب شخصی یا تیمی و مقصد سرویس آزمایشی.
- پلن‌های قابل انتخاب و هزینه جاری.
- برنامه‌ها و دیتابیس‌های مرتبط با مسابقه؛ اگر حساب خالی است، این موضوع ثبت شود.
- روش ساخت/مدیریت کلید API و امکان محدودکردن دسترسی؛ کلید در سند ثبت نشود.
- سرویس آزمایشی برای بررسی پاسخ لاگ، منابع، نسخه و وضعیت.

## ترتیب اجرا و معیار پایان

1. تکمیل کشف API و ورود کاربر؛ خروجی: فهرست قابلیت‌های تأییدشده و ابهام‌ها.
2. تست خواندنی با کلید محلی؛ خروجی: پاسخ پاک‌سازی‌شده پروژه‌ها و نمونه داده واقعی، بدون تغییر حساب.
3. نهایی‌کردن دامنه و بودجه؛ سپس یک انتشار واقعی با تأیید.
4. اضافه‌کردن تحلیل خطا، اصلاح محدود و سنجش نتیجه.
5. رابط فارسی و تاریخچه عملیات، مستندات GitHub، تمرین ویدئوی پنج‌دقیقه‌ای.

تقسیم زمان پیشنهادی ویدئو: ۳۰ ثانیه مسئله؛ ۹۰ ثانیه دیپلوی؛ ۱۲۰ ثانیه تشخیص و اصلاح؛ ۴۰ ثانیه تأییدها و شواهد؛ ۲۰ ثانیه محدودیت‌ها.
